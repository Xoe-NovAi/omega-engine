### Gap D308.2 — sqlite-vec Compile on Ubuntu 25.10

**Status**: ✅ **CONFIRMED** — Simple build process, no distro package needed

**Sources**:
- [sqlite-vec Compiling Guide](https://alexgarcia.xyz/sqlite-vec/compiling.html) — Official build instructions (accessed 2026-07-20)
- [sqlite-vec Installation](https://alexgarcia.xyz/sqlite-vec/installation.html) — `pip install sqlite-vec` (preferred) (accessed 2026-07-20)

**Finding**:
```bash
# From source (Linux)
git clone https://github.com/asg017/sqlite-vec
cd sqlite-vec
./scripts/vendor.sh    # Downloads SQLite amalgamation
make loadable          # Produces dist/vec0.so

# Or via PyPI (recommended)
pip install sqlite-vec  # Downloads pre-built wheel for manylinux_x86_64
```

**Dependencies**: `build-essential`, `sqlite3` dev headers (`libsqlite3-dev` on Ubuntu)

**Ubuntu 25.10 specifics**: 
- SQLite 3.46.1 (confirmed in D-308 Phase 0) — satisfies sqlite-vec's ≥3.41 requirement
- No `sqlite3-vec` APT package (confirmed)
- `pip install sqlite-vec` works — manylinux wheels available

**Impact**: 
- ✅ Build is trivial — single C file, no deps
- ✅ PyPI wheel avoids compilation entirely
- ✅ Compatible with Ubuntu 25.10's SQLite 3.46.1

**Confidence**: **High**

### Gap D308.3 — llama-cpp-python ROCm gfx906 (Death Certificate)

**Status**: ✅ **CONFIRMED DEAD** — Multiple independent confirmations

**Sources**:
- [llama.cpp Issue #19972](https://github.com/ggml-org/llama.cpp/issues/19972) (Feb 2026) — SOLVE_TRI crashes on gfx906 via rocBLAS Strsm (accessed 2026-07-20)
- [llama.cpp Issue #19442](https://github.com/ggml-org/llama.cpp/issues/19442) (Feb 2026) — Qwen3-Coder-Next crashes on dual MI50 (gfx906) (accessed 2026-07-20)
- [ROCm Compatibility Matrix 6.4.1](https://rocm.docs.amd.com/en/docs-6.4.1/compatibility/compatibility-matrix.html) — **gfx906 absent** from 6.3+/6.4+ supported architectures (accessed 2026-07-20)
- [daimonionnn/amd-vega-rocm-vulkan-llm-toolkit](https://github.com/daimonionnn/amd-vega-rocm-vulkan-llm-toolkit) — "ROCm 7.x officially dropped gfx900 support"; gfx90c only works via gfx900 backport in Docker (accessed 2026-07-20)
- Community forks: `bearqq/llama.cpp-gfx906`, `thickprogrammer/llama.cpp-gfx906`, `fuutott/llama.cpp-gfx906` — all maintain custom tensile backports (accessed 2026-07-20)

**Finding**:
| ROCm Version | gfx906 Support | Status |
|--------------|----------------|--------|
| 5.7 (2023) | ✅ Full | Last official support |
| 6.0+ | ❌ Dropped | AMD deprecated consumer iGPU ROCm |
| 6.4.1 | ❌ Absent | Matrix shows gfx908, gfx90a, gfx942, gfx1030, gfx1100, gfx1200 — **no gfx906** |
| 7.x | ❌ Dropped | gfx900 tensile kernels removed from rocBLAS |

**Root Cause**: rocBLAS Strsm (triangular solve) lacks gfx906 Tensile kernels. llama.cpp's `GGML_OP_SOLVE_TRI` falls back to rocBLAS → `hipErrorInvalidDeviceFunction` crash on models with `k > 32` (Qwen3-Coder-Next, Qwen3.5, Kimi Linear).

**Workarounds** (all suboptimal):
1. **Disable SOLVE_TRI** in `ggml_cuda_supports_op()` → falls back to CPU (works: 85.7/48.3 t/s on dual MI50)
2. **Docker with ROCm 6.3.4 rocblas backport** — daimonionnn's `Dockerfile.rocm7-vega` technique
3. **Community forks** with custom tensile builds (bearqq, thickprogrammer, fuutott)
4. **Use Vulkan instead** — daimonionnn: "Vulkan native (FA OFF default): Best generation throughput"

**Impact**: 
- ✅ **ROCm on 5700U is dead for production** — use Vulkan
- ✅ Vulkan on Vega 8 delivers 19-20 tok/s generation (daimonionnn verified)
- ⚠️ If ROCm absolutely required: Docker + tensile backport only path

**Confidence**: **Very High** — multiple primary sources (AMD ROCm matrix, llama.cpp issues, community forks)
