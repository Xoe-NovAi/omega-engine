## §2 — Q1: Why does a FREE model trigger "Insufficient balance"? (🔴 HIGH)

**Direct answer**: Because OpenRouter enforces a **two-tier gating system** that the free-tier suffix does NOT bypass:

1. **Account-level credit gate**: If the account balance is negative, ALL API calls fail with 402, even `:free` models. This is documented in OpenRouter's official limits reference.

2. **Per-key credit limit**: If a per-key spending cap is set and exhausted, the same 402 fires.

3. **Daily free request cap (50 RPD for non-funded accounts)**: When exceeded, OpenRouter returns 402 (not 429). This is different from the 429 "rate limit exceeded" errors we see on other free models in our probe data.

**Why the contradiction?** OpenRouter has two rate limit systems:
- **HTTP 429**: Free model per-minute cap (20 RPM) and many provider-side rate limits
- **HTTP 402**: Account-level credit issues (negative balance, exhausted per-key cap, or daily free request cap for non-funded accounts)

**Our situation**: We are seeing **402**, not 429, which means OpenRouter is NOT rate-limiting us on a per-minute basis. It's telling us our **account cannot serve the request** because of account-level state.

## §3 — Q2: What is the OpenCode platform's balance logic? (🔴 HIGH)

**OpenCode has NO balance logic.** It is a thin OpenAI-compatible client. When you specify a model and provider:
- OpenCode calls OpenRouter's API with the user's OpenRouter API key
- OpenRouter does the authentication, authorization, and billing checks
- OpenRouter returns the response (or error)
- OpenCode relays the error

**The balance check is entirely on OpenRouter's side.** The "balance" in "Insufficient balance" refers to the OpenRouter account that owns the API key, not OpenCode.

**OpenCode does maintain its own usage tracking** (cost, tokens, etc.) in its local SQLite DB, but this is for **display purposes only** — it has no effect on whether the model call succeeds.

## §10 — L1 → L2 → L3 Distillation

### L1 (Narrative — what happened)
Today (2026-08-27), during 5 parallel subagent dispatches, OpenCode's Ma'at agent repeatedly hit HTTP 402 "Insufficient balance" errors when calling `minimax/minimax-m3:free` (a free model on OpenRouter). The error originated from OpenRouter, not OpenCode. The OpenCode log shows the exact error chain. Three of the 5 dispatches to the same target session all failed with the same 402. Earlier dispatches (e.g., the vault research) worked fine, suggesting a recent account state change (e.g., balance went negative, or daily free cap was hit).

### L2 (Insight — what this means)
The "Insufficient balance" error on a free model is **not paradoxical** — it is OpenRouter's documented behavior. When an account's balance is negative (even by $0.02), OpenRouter blocks ALL API calls from keys on that account, including requests to free models. The model itself is genuinely free ($0 per token), but the account is not in a "clean" state. Our fleet has been running on a free model through OpenRouter without verifying the account state. This is a fragility in our provider assumption: we assumed "free" means "unconditional," but "free" on OpenRouter is conditional on the account being in good standing. The 402 error is OpenRouter telling us "your account is not in good standing" using a billing-error vocabulary.

### L3 (Universal Principle — what this teaches)

> **"Free" in a marketplace is never unconditional; it is always a temporary state of grace that can be revoked by the platform at any time, including for reasons unrelated to the free tier itself. A fleet that depends on a single free provider for mission-critical work is one account event away from total failure. Sovereignty means local-first, paid-fallback, multi-provider resilience — never free-only.**

This applies beyond OpenRouter: any cloud provider's free tier (Google AI Studio, AWS Bedrock free, Azure free credits) has the same fragility. The free tier is a marketing funnel, not a foundation. M7 (Local-First) is correct precisely because it eliminates this entire failure mode. The MiniMax M3 promotion (D-585) was justified by empirical success — but empirical success on one day is not the same as architectural resilience.

## §12 — Quick Diagnosis Script

For fleet use, here's a one-liner to check OpenRouter key health + balance:

```bash
#!/bin/bash
# check_or_health.sh — Diagnose OpenRouter 402 errors
KEY="${1:-$OPENROUTER_API_KEY}"
echo "=== OpenRouter Key Diagnostic ==="
echo "Key: ${KEY:0:12}..."

# 1. Auth check
AUTH=$(curl -sS https://openrouter.ai/api/v1/auth/key \
  -H "Authorization: Bearer $KEY")
echo "Auth: $(echo "$AUTH" | jq -r '.data.label // .error.message')"

# 2. Credit check
CREDITS=$(curl -sS https://openrouter.ai/api/v1/credits \
  -H "Authorization: Bearer $KEY")
echo "Credits: $(echo "$CREDITS" | jq -r '.data.total_credits // "N/A"') USD total"
echo "Usage:   $(echo "$CREDITS" | jq -r '.data.total_usage // "N/A"') USD used"

# 3. Free model test
echo "=== Free model test (minimax/minimax-m3:free) ==="
curl -sS -X POST https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"minimax/minimax-m3:free","messages":[{"role":"user","content":"hi"}],"max_tokens":5}' \
  | jq -r '.error.message // .choices[0].message.content // "UNKNOWN"'
```

Expected outputs:
- Healthy: `Credits: 5.0 USD total` + `"hi"` from M3
- Negative balance: `Credits: 0 USD total, -2.5 USD used` + `Insufficient balance`
- No credits ever: `Credits: 0 USD total, 0 USD used` + `Insufficient balance` (after 50 RPD)
