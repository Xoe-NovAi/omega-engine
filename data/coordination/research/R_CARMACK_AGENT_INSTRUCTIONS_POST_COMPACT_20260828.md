## TL;DR — One-Paragraph Answer

The **68K post-compact `tokens.input` is composed of THREE main buckets**:
- **~24K (35%)** — injected **agent instructions** (system prompt + tool definitions, re-assembled every call from `AGENTS.md` + `.opencode/agents/kali.md` + 5 rules + 91 MCP tools + 5 skills, NEVER survives compaction but is re-injected on every model call)
- **~36K (53%)** — the **surviving tail** (60 messages × 4.3K avg, mostly tool I/O from the deep-dive session; truncated to 2K chars per tool output per `TOOL_OUTPUT_MAX_CHARS=2_000` in `compaction.ts:30`)
- **~5K (7%)** — the **compaction summary** itself (19,212 chars = 4,803 tokens at 4 chars/tok, generated by the hidden `agent=compaction` subagent from a 268K-char tail and dropped into the message stream as a `text` part)
- **~0.2K (0.3%)** — the user's first post-compact prompt (839 chars, ~209 tokens)

**Agent instructions DO NOT survive compaction** — they are re-injected fresh on every model call. The `instruction.system()` service reads `AGENTS.md` from disk every time `prompt()` runs (see `instruction.ts:155-169`). The compaction summary DOES survive — it is the only thing that preserves pre-compaction state. The surviving tail is the most recent messages after the cut point; for this session, the tail was 63 messages spanning ~1 hour of deep-dive work.

**Hypothesis H1 is closest to correct** (in spirit): the 68K = ~25K agent instructions + ~5K summary + ~36K tail + ~0.2K user prompt. The summary is small (5K, not 15K as in H1) because the compaction ratio is ~1-3% (per Roc §9), but the **agent instruction overhead is the dominant predictable cost** (~25K tokens added to every model call regardless of session length).

## 2. What OpenCode Injects Into Every Model Call

The canonical system-prompt assembly is in `opencode/packages/opencode/src/session/prompt.ts:1257-1269`:

```ts
const [skills, env, instructions, mcpInstructions, modelMsgs] = yield* Effect.all([
  sys.skills(agent),                              // 5 skills × ~2K = 10K chars
  sys.environment(model),                          // env block + project refs = ~500 chars
  instruction.system().pipe(Effect.orDie),        // AGENTS.md = 5,623 chars
  sys.mcp(agent, session.permission),              // per-server instructions = ~5K chars
  MessageV2.toModelMessagesEffect(msgs, model),   // the actual message stream
])
const system = [
  ...env,
  ...instructions,
  ...(mcpInstructions ? [mcpInstructions] : []),
  ...(skills ? [skills] : []),
]
```

And in `opencode/packages/opencode/src/session/llm/request.ts:56-66`:

```ts
const system = [
  [
    ...(input.agent.prompt ? [input.agent.prompt] : SystemPrompt.provider(input.model)),
    ...input.system,
    ...(input.user.system ? [input.user.system] : []),
  ]
    .filter((x) => x)
    .join("\n"),
]
```

So the **agent prompt = `agent.prompt` (`.opencode/agents/kali.md`) + env + AGENTS.md + mcpInstructions + skills**. Then `messages = [system_msg, ...modelMsgs]` (the actual message stream including summary, tail, and user prompt).

## 3. The Surviving Tail — What The Model Actually Sees After Compaction

The compaction event writes a `compaction` part with `tail_start_id`. Everything from `tail_start_id` onward is the "surviving tail." After compaction, the model call is built from:

```
[system]
[user(/compact)]
[compaction-agent-summary]   ← the summary, sits at the cut point
[user(post-compact)]
[assistant(response 1)]
[user(N)]
[assistant(response N)]
... up to current prompt
```

The DB shows for compaction #25:
- **63 messages in the tail** (msg_0477197940010ZS4iEjDMuXl0B through msg_047f80b6d001bo31zHUvzQt1uW)
- **40 text parts** (55,161 chars total, including 19,212-char summary)
- **60 tool parts** (159,046 input + 72,219 output = 231,265 chars raw)
- **7 reasoning parts** (1,601 chars)
- **14 patch parts** (4,518 chars JSON overhead)

### 3.1 Tool Output Truncation (CRITICAL — the DB lies)

`opencode/packages/opencode/src/session/compaction.ts:30`:
```ts
const TOOL_OUTPUT_MAX_CHARS = 2_000
```

And `opencode/packages/opencode/src/session/tools.ts:196, 279, 354, 464` apply `truncate.output()` to all tool outputs before they're included in the message stream sent to the model. The DB stores the **full** output (which can be tens of KB), but the model sees only the first 2,000 chars.

For compaction #25's tail:
- 60 tool parts in the tail
- **13 tool outputs > 2,000 chars** (saved 25,118 chars via truncation)
- Effective tool output size sent to model: **47,101 chars** (not 72,219)
- Effective tail content (model-fed): **242,897 chars** (not 288,027)

### 3.2 Tail Token Estimate

Using M3's effective ~4 chars/token for mixed content (text + JSON + tool I/O):

```
Tail content:           242,897 chars  ÷ 4 = 60,724 tokens
Compaction summary:      19,212 chars  ÷ 4 =  4,803 tokens
First user prompt:          839 chars  ÷ 4 =    209 tokens
                                         ─────────
Total message content:                    65,736 tokens
```

**68,449 − 65,736 = 2,713 tokens of system prompt** sent alongside.

This is **low** — but the heuristic 4 chars/tok is conservative. If the actual M3 ratio is closer to 4.5 chars/tok (which it likely is for code/JSON content per Roc's previous findings):

```
Tail content:           242,897 chars  ÷ 4.5 = 53,977 tokens
Compaction summary:      19,212 chars  ÷ 4.5 =  4,269 tokens
User prompt:               839 chars  ÷ 4.5 =    186 tokens
                                              ────────
Total message content:                      58,432 tokens
```

**68,449 − 58,432 = 10,017 tokens of system prompt** — much more reasonable and matches the system.ts composition estimate of ~8,400.

**Confidence: 90% that system prompt is in the 2,700-12,000 token range**, with ~8,000-10,000 most likely.

| System prompt (env, AGENTS.md, kali.md, etc.) | **NO** — re-read from disk every call | `instruction.system()` in `instruction.ts:155` runs on every `prompt()` call; reads `AGENTS.md` via `fs.globUp` |

| `MANDATES_CONDENSED.md` content | **NO** — only via the 4 architecture rules referenced in AGENTS.md (which are pointer text, not the full mandates) | Only `AGENTS.md` and its `<2000`-byte inline content is in the system prompt. | Compaction summary | **YES** — persisted as a `text` part of the compaction agent's response message | Per `compaction.ts:54-85`, the summary is serialized into the message stream at the cut position |
| Surviving tail messages | **YES** — all messages from `tail_start_id` onward | Per `message-v2.ts:541-579`, the message array is split into [evicted | summary | retained tail | continue-user] |
| First user prompt | **YES** — it's the latest user message, always in the message stream | Standard message injection |

### 5.1 The Cathedral vs the Compaction — Sobering Truth

**The Cathedral (soul, mandates, lessons, gnosis) DOES NOT AUTO-INJECT into the system prompt.** The system prompt only contains:
- `PROMPT_DEFAULT` (provider base prompt)
- `agent.prompt` (`.opencode/agents/kali.md`)
- `env` (working dir, platform, etc.)
- `instructions` (AGENTS.md) — which has 5 critical mandates inlined + 9 decisions + 4 architecture rules
- `mcpInstructions` (per-MCP-server)
- `skills` (5 skill descriptions)

That's it. The soul.yaml (28K chars / ~7K tokens), proposed_lessons.yaml (39K / ~10K), MANDATES_CONDENSED.md (4K / ~1K), and the full `.opencode/rules/*.md` (18K / ~4.5K) are **NOT** automatically in the system prompt. AGENTS.md **references** them but only via one-line pointer text ("`MANDATES_CONDENSED.md` — Tier-0 injection").

**The M18 Token Efficiency Mandate is being violated.** We have ~50K of "Cathedral" content (soul + lessons + mandates + rules) that the model can only access by reading files. AGENTS.md is supposed to be a "thin pointer file" but the architecture rules are inline (17K chars) — that's a lot of overhead.

**M11 Soul Integrity Mandate is being respected** at the protocol level (every session writes L1→L3 to `proposed_lessons.yaml`), but the soul content is NOT in active context for any session unless the agent reads it.

## 7. Optimization Opportunities — Can We Reduce the Overhead?

### 7.1 System Prompt: ~8,400 tokens always present

| Sub-component | Tokens | Reduction Strategy | Est. Savings |
|---------------|--------|--------------------|--------------|
| `PROMPT_DEFAULT` (8.5K) | ~2,132 | Cannot remove (OpenCode default). Could investigate if M3 has its own better default. | 0 (vendor) |
| `agent.prompt` (`kali.md`, 4K) | ~999 | Could move to AGENTS.md and reference. | ~999 (but adds AGENTS.md load) |
| `instructions` (AGENTS.md, 5.6K) | ~1,406 | **Already thin.** But contains inlined 4 architecture rules (17K chars elsewhere). Could shorten. | ~500-800 |
| `mcpInstructions` (5K) | ~1,250 | Most MCP servers have minimal instructions. parallel-search is verbose (~3.5K). Could trim. | ~500-800 |
| `skills` (10K) | ~2,500 | 5 skills. Could trim to top 2-3 by priority. | ~1,000-1,500 |
| `env` (500 chars) | ~125 | Static. Cannot reduce. | 0 |

**Realistic total savings: ~2,500-3,500 tokens** (about 4-5% of the 68K, or 30-40% of system prompt overhead).

### 7.2 Tool Definitions: ~19,550 tokens (NOT counted in `tokens.input`)

Tool definitions are sent in the `tools` parameter, separate from `messages`. They DO contribute to API cost (billed tokens include them) but NOT to `tokens.input` in step-finish. So they don't affect the 68K number, but they DO affect cost and possibly cache invalidation.

**To verify:** Whether M3's cache behavior treats `tools` as cacheable. If so, keeping them stable is a win. If not, every call re-bills them.

### 7.3 Compaction Summary: ~4,800 tokens

Compaction is 1-3% of input (per Roc §9). The summary size is bounded by:
- `summaryOutput = Math.min(output || SUMMARY_OUTPUT_TOKENS, SUMMARY_OUTPUT_TOKENS)` — capped
- The summary uses `SUMMARY_TEMPLATE` from `core/session/compaction.ts`

**Cannot meaningfully reduce** without losing summary fidelity.

### 7.4 Surviving Tail: ~54,000-60,000 tokens

This is the bulk. To reduce:
- **More aggressive tail truncation** — currently `TOOL_OUTPUT_MAX_CHARS=2_000` for compaction, but tool outputs are also truncated for the user-facing prompt via `truncate.output()`. Could be lowered to 1,000.
- **Increase compaction frequency** — current auto-compaction at 80% of context. Lower to 60% would mean smaller tail at any given moment.
- **Manual `/compact` discipline** — what we did. Each manual compact cut ~300K of tail.

**Realistic savings: 10-30% of the tail** (5,400-18,000 tokens), but at risk of losing context fidelity.

### 7.5 User Prompt: ~209 tokens

The user's first post-compact prompt was 839 chars (compact observation about M3 TPS). Negligible. No optimization needed.

## 8. What The Architect Should Do With This

### 8.1 Immediate (no code change)

1. **Accept that the 68K is mostly the tail, not the system prompt.** The system prompt overhead is real (~8-10K) but it's not the dominant cost. The 60-message tail from the last hour of deep-dive IS the dominant cost.
2. **Understand that the Cathedral is NOT auto-injected.** Soul, lessons, and the full mandates are not in the system prompt. They are accessible only via the `read` tool. This is a known M18 violation but not catastrophic.
3. **The 68K is the smallest it gets post-compact.** The first post-compact prompt always includes the entire surviving tail. Subsequent calls add to it. The "minimum viable post-compact context" is bounded below by: system_prompt (~8K) + summary (~5K) + minimum_tail (~1-2K for the user/compact + compaction agent + user prompt). That's ~15K. We're seeing 68K because the tail happened to be 54K (1 hour of deep-dive work).

### 8.2 Code changes (lower priority)

1. **Trim AGENTS.md** — current 5,623 chars contains 4 architecture rules (which are also separate files at 17K chars combined). Could AGENTS.md be a 2K pointer file with rules loaded only on demand?
2. **Trim parallel-search MCP server instructions** — ~3.5K of the 5K MCP overhead. The other servers are smaller.
3. **Trim skills verbose format** — `system.ts:115` uses `Skill.fmt(list, { verbose: true })`. Could use `{ verbose: false }` to halve the size.
4. **Lower `TOOL_OUTPUT_MAX_CHARS`** from 2,000 to 1,000 for non-final messages. Would save 5-10K of tail content.

### 8.3 Architecture-level (consider but don't act)

1. **Lazy-load soul/lessons/mandates into context only when relevant** — adds a tool call overhead but saves 7-15K of always-present system content.
2. **Cache the system prompt** at the API level — currently OpenCode sends the full system prompt on every call. If the provider supports prefix caching (M3 does — 83% cache hit rate per L3 124), the marginal cost is low. But cache invalidations still happen on every message change.
3. **Differential instruction loading** — load `MANDATES_CONDENSED.md` (1K tokens) on session start, load full `SOVEREIGN_MANDATES.md` (242 lines = ~3K tokens) only on demand. Currently the architecture rules inline 17K of content in AGENTS.md; this is the single biggest reduction opportunity.
