### MRL Truncation Quality (Empirical Evidence)

**Key finding from MRL paper (NeurIPS 2022)**: "ResNet50–MRL model is at least as accurate as each FF model at every representation size in M while MRL–E is within 1% starting from 16-dim."

**Key finding from supermemory.ai**: "halving the dimension kept quality near intact... going down to roughly one third still preserved most of it"

**Key finding from Nomic v1.5 MTEB by dimension** (proxy for MRL behavior):

**Inference for Qwen3-Embedding-0.6B 1024→768 MRL**:
- 768/1024 = 75% of native → expected quality retention: ~98-99%
- For comparison, Nomic 768→512 (67% retention) shows 0.32 point drop (0.5%)
- Qwen3 1024→768 (75% retention) expected: ≤0.5 point MTEB drop
- **Verdict: 1024→768 MRL is SAFE for production** (<1% quality loss)

### MRL Chain Validation (Qwen3 two-stage)

**Current pipeline (Gemma)**: 768 native → adapter MRL → 512/256/128/64

**Target pipeline (Qwen3)**: 1024 native → provider MRL → 768 → adapter MRL → 512/256/128/64

**Validation**:
- MRL paper proves that intermediate dimensions show "interpolating behavior" — even dimensions not in the nesting list (M = {8,16,32,64,128,256,512,1024,2048}) show good quality
- The 768 is NOT in Qwen3's standard nesting list (which is 32, 64, 128, 256, 512, 1024), but MRL's interpolating property means it will work
- **Risk**: Slightly higher drift at 768 than at 512 or 256 (which are in the nesting list)
- **Mitigation**: Run recall@10 benchmark post-migration; if <98% of native 1024, fall back to 512-dim canonical

### sqlite-vec Dimension Migration Patterns

From sqlite-vec GitHub:
- vec0 tables are created with fixed dimension in schema: `float[768]`
- **NO native dimension change support** — must DROP + RECREATE table
- Pattern: `DROP TABLE IF EXISTS vec_old;` then lazy re-create on first upsert
- For greenfield (empty DBs): zero data migration, just config change
- For production (existing vectors): must re-embed from source

### Multi-Collection Same-Model Architecture

**Pattern**: Same embedding model, multiple vec0 tables for different domains/partitions
- Each table has independent HNSW index
- Cross-table search requires UNION + re-rank (not native)
- Storage cost = N × vector_size (no sharing)
- For Qwen3 @ 768-dim: 1 vector = 3KB (float32) or 1KB (int8)
- 100K vectors × 2 collections = 600KB (float32) or 200KB (int8) — acceptable

### Cross-Collection Search

**Not natively supported by sqlite-vec**. Options:
1. **Partition key** (single collection, filtered KNN) — most efficient
2. **Global partition `_all`** (mirror writes) — 2× storage
3. **Union + re-rank at app layer** — query each collection, merge results
4. **Memory + library in same collection** — breaks sovereignty, loses domain isolation

**Best practice**: Use partition keys (option 1) for primary queries; option 3 (union) for rare cross-collection searches.
