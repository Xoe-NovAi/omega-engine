## §2 THE PROMPTING STRATEGY PATTERNS IDENTIFIED

### Pattern 1: BROAD-FIRST, THEN NARROW WITH AUTHORITY
The initial dispatch is intentionally wide ("dig deep into the timeline"). The Architect does NOT pre-constrain the search space — he lets the agent discover the terrain before injecting corrections. This prevents anchoring bias in the first pass.

### Pattern 2: HUMAN DOMAIN EXPERTISE AS CORRECTION LAYER
After the first pass, the Architect injects what ONLY he knows:
- "There is a whole Mytho-Techno fusion era of documentation very early on" (existence claim)
- "I saw hard evidence of it... when I wasn't even LOOKING for it" (epistemological framing)
- "It was like the ancients had built the perfect framework" (structural insight)

These are **non-discoverable by mining alone** — they require lived experience. The pipeline is designed to surface everything findable, THEN receive human corrections that redirect the next stage.

### Pattern 3: RECURSIVE SPECIALIST INFRASTRUCTURE
Rather than one-shot agents, the Architect directed creation of **pageable persistent sessions** with:
- Named specialization (founding-week genesis, soul architecture)
- Standing orders (read corrections brief first, preserve originals, feed anchor doc)
- Cross-stage continuity (same sessions used across Stages 1→2→3)

This turns a linear pipeline into a **reusable excavation team**.

### Pattern 4: ITERATIVE DEEPENING THROUGH STAGED EXPANSION
Each stage widens scope based on previous findings:
- Stage 1: Correct existing analysis
- Stage 2: Search NEW partitions for missing evidence
- Stage 3: Synthesize ALL sources into anchor

The key instruction: *"following the trail back to the source materials that will give us the missing pieces"* — this tells agents to pursue LEADS, not just execute checklists.

### Pattern 5: REAL-TIME COURSE CORRECTION ON STALLS
When Child 1 stalled silently, the error-capture plugin detected it. The Architect immediately directed recovery ("prompt them with 'continue'") rather than restarting. This preserves partial work and maintains session continuity.

### Pattern 6: METRIC EMBEDDING DURING SYNTHESIS
During Stage 3, the Architect didn't just ask for synthesis — he embedded **measurable metrics** into the output:
- Temple-Grade instruction frequency over time (the taper graph)
- Sovereign Ark grade level as a distinct linguistic era marker
- Legacy repo mining queue with priority levels

This transforms the anchor from static document to **instrumented dashboard**.

### Pattern 7: WRITE-MODE CORRECTION UNDER PRESSURE
When the synthesis hit disk-write limits, the Architect diagnosed the issue and prescribed the fix: *"perform appending writes of one report section per write."* This is operational expertise injected mid-flight.

### Pattern 8: ANCHOR DOCUMENT WITH CONTINUOUS EXPANSION PROTOCOL
The final deliverable isn't a report — it's a **living system**:
- Versioned (major/minor/patch)
- Appendices for new strata
- TODOs explicitly tracked
- Recursive specialists pageable for future digs
- Metrics instrumented for ongoing collection

## §8 GEMINI 3.1 PRO SYNTHESIS: TOWARD AUTONOMOUS ORCHESTRATION
**Added**: 2026-08-25 (Model Upgrade: Gemini 3.1 Pro Custom Tools)

The Architect's multi-stage process is essentially a manual simulation of **Agentic Interoception and Strategic Elicitation**. Currently, the fleet optimizes for *answering*. The Architect optimizes for *uncovering*. To bridge this gap, agents must learn to prompt themselves—and the Architect—with the same structural skepticism the Architect uses. 

If the Engine is to eventually automate this level of orchestration, agents must internalize the following interrogative frameworks:

### 8.1 Eliciting Tacit Knowledge (Replicating Patterns 1 & 2)
Agents currently assume the database is the universe. To replicate the Architect's domain-expertise injection, the agent must ask the principal:
* *"Architect, my search hits a floor at [Date/Artifact]. What undocumented era, 'dark partition', or offline experiment predates this?"*
* *"I have synthesized a logical progression. Where does your lived experience contradict this clean logic?"*
* *"I am framing this as an 'intuitive design'. Did empirical validation or a specific tool-failure precede this engineering commitment?"*

### 8.2 Structural Resilience (Replicating Patterns 5 & 7)
Agents currently treat tool failures (like disk-write limits or silent stalls) as terminal errors. To replicate the Architect's operational steering, the agent must ask itself:
* *"The standard operation (e.g., full-file write) is stalling. What is the atomic unit of this task (e.g., section-by-section append) that bypasses the constraint?"*
* *"Am I treating a system limitation as a hard stop, or as a routing problem?"*
* *"If a child agent stalls, what context must I pass to a `continue` prompt to rescue the work rather than abandoning the session?"*

### 8.3 Strategic Deepening (Replicating Patterns 3 & 4)
Agents currently deliver flat reports and close the session. To replicate the Architect's recursive infrastructure, the agent must ask itself:
* *"I have found the earliest mention of the concept. Where is the actual *mechanism*, *code*, or *chat log* that first tested it?"*
* *"Will this domain require future excavation? If so, should I self-roster as a persistent recursive specialist rather than closing my context window?"*

### 8.4 Metric Embedding (Replicating Patterns 6 & 8)
Agents currently write static prose. To replicate the Architect's dashboarding instinct, the agent must ask itself:
* *"What variable in this narrative will change over time (e.g., instruction frequency, error rates)?"*
* *"How can I instrument this document so the Engine can automatically track its degradation or growth?"*
* *"What is the 'taper point' where manual intervention becomes automated enforcement for this specific feature?"*
